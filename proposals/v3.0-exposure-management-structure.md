# PRC-VM-001 v3.0 — Proposed Structure (Revised)

## The Shift: Vulnerability-Centric → Control-Centric

v2.0 was the first step — it renamed VM to Exposure Management, added the 6-state model,
and separated patch hygiene. v3.0 completes the evolution.

The question v2.02 answers:  *"Is this vulnerability reachable?"*
The question v3.0 answers:  *"Would our controls actually stop the attack?"*

---

## Proposed Table of Contents

### 1. Purpose and Philosophy  (revised)

Keep the operating premise from v2.02 but add the new thesis.

Add §1.4 — **The Control-Centric Thesis**:
- Exposure management's primary job is no longer patching coordination
- Its primary job is understanding, measuring, and proving control effectiveness
- Patching is a control, not the program. If the control stack is verified effective,
  the residual exposure may be genuinely low even for a high CVSS finding
- In the agentic threat era, "patch faster" is not a strategy because the problem
  grows faster than any ops team can remediate

> *"A scanner tells you what's installed. A control stack tells you whether it matters."*

### 2. The Exposure State Model  (new state added)

Current: Observed → Validated → Reachability Assessed → Exposure Confirmed →
Treatment Selected → Closure Verified

Add:

| State | Definition |
|-------|-----------|
| **Control Stack Assessed** | Controls protecting this asset have been evaluated: detection coverage verified, EDR tested, blast radius mapped, SOC alert path confirmed. |

Sits between Reachability Assessed and Exposure Confirmed, because:
- An asset can be reachable but not a material exposure if the control stack is
  proven effective → routes to **Compensated Exposure** classification
- An asset can be unreachable but the control stack is broken → routes to
  **Control Stack Failure** classification (detection gap, broken EDR, missing DLP)

### 3. Roles and Responsibilities  (updated)

Add:

| Role | Responsibility |
|------|--------------|
| **Exposure Intelligence Lead** | Operates control stack assessment. Maintains the compensating control certification registry. Drives architectural exposure reduction. Tracks agentic and AI threat surface. |

Same person as Exposure Management Lead in small teams; distinct function regardless.

### 6. Step 3 — Validate Exposure Path  (rewritten)

Current §6 asks: "Is the service running? Reachable? Segmented?"

New §6 asks three sets of questions.

**§6.1 Network Path Assessment** (keep existing)
Reachability, segmentation, authentication requirements, compensating controls.

**§6.2 Control Stack Assessment** (NEW — the core of v3.0)

For every exposure that passes network path assessment, evaluate the control stack:

| Dimension | Question | How to Test |
|-----------|----------|-------------|
| **Detection** | Would the SOC detect exploitation of this exposure? | Has this CVE/technique been validated against SIEM rules? Last purple-team test? |
| **Prevention** | Can EDR/AV be bypassed for this exposure class? | Has a control bypass test been conducted on this platform in the last 12 months? |
| **Data path** | Is DLP in the data path this exposure enables? | Does DLP inspect the protocol, port, and data flow? |
| **Segmentation** | Is lateral movement bounded? | Has lateral movement from this asset class been tested? |
| **Blast radius** | What can an attacker reach from this asset? | Documented chokepoints? Privilege containment? |
| **Resilience** | Is recovery from this asset class tested? | Last restore test date and result? |

**§6.3 Agentic Path Assessment** (NEW)

| Question | What It Tests |
|----------|--------------|
| Can an AI agent with tool access reach this asset? | Agent tool-calling scope, delegated credentials, API paths |
| Is there an agent-mediated privilege escalation path? | Agent with tool access that can escalate to this surface |
| Would agent behavior detection fire? | Detection coverage for agent-driven activity on this asset class |
| Can a prompt injection reach this surface? | Agent input sanitization, model access controls, tool sandboxing |

**§6.4 Control Bundle Certification** (NEW)

The output of §6.2 and §6.3 is a **Control Bundle** — a structured set of
verified controls that together reduce the residual exposure of a given finding.

A control bundle is certified when:

1. Every control in the bundle has been tested and verified as effective within
   the last 12 months (6 months for KEV-related exposures)
2. The bundle includes at least one preventive control AND one detection control
3. The blast radius assessment is documented and tested
4. The bundle has an expiration date (90 days maximum)
5. A bundle break trigger is defined — any change to the control stack
   (tooling change, config change, network change, agent deployment change,
   EDR rule update) invalidates the bundle until re-certified

**Control Stack Rating**

The assessment produces a rating that feeds directly into classification (§7):

| Rating | Meaning |
|--------|---------|
| **Effective** | All controls in the bundle tested and verified. Detection confirmed. Blast radius documented. |
| **Partial** | Some controls verified, gaps exist. Detection may be partial. |
| **Unproven** | Controls exist but have not been tested or verified. |
| **Failing** | Controls are known to be broken, bypassed, or missing critical components. |

### 7. Step 4 — Classify  (revised taxonomy)

| Classification | Definition | Treatment Approach |
|---------------|-----------|-------------------|
| Non-issue / Scanner Artifact | (unchanged) | Close with evidence |
| Hygiene Debt | (unchanged) | Patch cycle cadence |
| **Compensated Exposure** | Reachable path exists but control stack rating is **Effective** — bundle certified, controls verified, detection confirmed | Monitor control health; remediate at maintenance cadence |
| Confirmed Exposure | Reachable path exists; control stack rating is **Partial** or **Unproven** | Treat per SLA |
| **Control Stack Failure** | Asset may be patched and not reachable, but one or more protecting controls are proven **Failing** (EDR not detecting, DLP missing, SOC not alerted) | Treat the control, not the asset |
| Material Risk | Confirmed exposure on crown jewel / regulated system / Restricted data, OR active exploitation, OR **Unproven** control stack on internet-facing critical surface | Emergency treatment, PPR tier |

**Key distinction:** An exposure is "Compensated" only when the control bundle
is certified effective. If controls exist but haven't been tested, the finding
remains "Confirmed Exposure" — the controls are *claimed*, not *proven*.

**§7.2 Treatment SLAs** — full CVSS decoupling

SLAs driven by classification + reachability context, not by CVSS:

| Context | SLA |
|---------|-----|
| Material Risk — PPR (KEV, active exploitation, crown jewel) | 48h internet-facing / 72h internal |
| Material Risk — Agentic (AI agent with unproven control stack on this surface) | 72h |
| Confirmed Exposure — Internet-reachable | 3 days |
| Confirmed Exposure — Internal reachable | 15 days |
| Compensated Exposure | 90 days (monitor control health; re-certify bundle quarterly) |
| Control Stack Failure | Based on control criticality, not asset criticality. Fix the control. |
| Hygiene Debt | Patch cycle cadence |

**§7.3 — CVSS Handling (NEW)**

CVSS is treated as an input signal, not a classification driver.

| CVSS Range | Role in Exposure Pipeline |
|------------|--------------------------|
| CVSS ≥ 9.0 | Triggers accelerated validation (4h). After validation, classification is driven by control stack rating and reachability, not CVSS. |
| CVSS 7.0–8.9 | Standard validation timeline (24h). Post-validation, CVSS is not referenced for SLA or priority. |
| CVSS < 7.0 | Hygiene Debt unless reachable on crown jewel or active exploitation. |
| KEV | KEV always accelerates — regardless of CVSS. Active exploitation is a Material Risk classification immediately. |

### 8. Step 5 — Select Treatment  (updated)

Add to the treatment options table:

| Treatment | When to Use | Example |
|-----------|------------|---------|
| **Eliminate agent access** | AI agent has tool access to an unnecessary exposure surface | Remove agent tool-calling privilege for this API; scope agent data access |
| **Isolate in agent sandbox** | Agent-mediated exposure that cannot be eliminated | Route agent API calls through a security proxy with content inspection and rate limiting |
| **Add control instrumentation** | Exposure has no detection path | Deploy EDR telemetry, add DLP inspection, enable SIEM logging on this asset class |
| **Architecture change** | The asset's design creates unavoidable exposure | Move admin interface to jump-host; replace thick client with browser-based access; implement presentation-layer-only access |

**§8.1 — Patching vs. Control Investment**

> *"The question is not 'can we patch this?' The question is 'what is the most
> effective path to reduce residual risk?' A dollar spent proving EDR works
> may reduce more risk than a dollar spent patching a workstation CVE that
> three tested controls already block."*

The treatment decision is a resource allocation decision, not a compliance checkbox.

### 11. Risk Acceptance and Exceptions  (key revision)

Current §11 defines two paths: Policy Exception and Risk Acceptance.

**This stays.** The control bundle assessment does not create a third path.
It makes the existing risk acceptance path more honest.

**§11.3 — Honest Residual Risk (NEW)**

When a risk acceptance record is created for a Confirmed Exposure or
Compensated Exposure that relies on a control bundle, the acceptance memo
MUST include:

| Field | Description |
|-------|-------------|
| Control bundle reference | ID of the certified control bundle (from §6.4) |
| Bundle certification date | When the bundle was last tested and verified |
| Bundle expiration date | 90 days from last certification |
| Control stack rating | Effective / Partial / Unproven / Failing |
| Residual risk justification | Why the verified control stack reduces likelihood and impact to the documented residual level |
| Key controls in the bundle | EDR+AV+no admin rights+proxy+execution control, etc. |

Without this information, the risk acceptance record is incomplete and cannot
be approved at a reduced authority level.

**§11.4 — Approval Authority and the Control Bundle Effect (NEW)**

The existing risk acceptance authority table (from RMF-001) already delegates
approval based on residual risk level. A verified control bundle provides the
evidence to support a lower residual risk classification — meaning the CISO
does NOT need to approve acceptances where the control stack demonstrably
reduces risk to a Low residual level.

| Scenario | Control Stack Rating | Residual Risk Level | Approver |
|----------|---------------------|-------------------|----------|
| CVSS 9.7 RCE, internet-facing, no controls | Unproven / None | Critical | CISO |
| CVSS 9.7 RCE, internal, EDR+AV+no admin | Effective | Low | Risk Pillar Leader |
| CVSS 9.7 RCE, compensated, proxied traffic | Effective | Low | Risk Pillar Leader |
| CVSS 6.5, crown jewel, no controls | Unproven | High | CISO |
| CVSS 6.5, internal server, EDR+segmented | Partial | Medium | Risk Pillar Leader |

The control bundle is the *evidence* that justifies the lower authority level.
Without it, the default assumption is Unproven — CISO-level approval required.

> *"The goal is not to bypass the CISO. The goal is to give the CISO confidence
> that Low-risk acceptances are genuinely Low, based on tested evidence, so they
> can delegate without feeling like they're gambling."*

**§11.5 — Bundle Break Trigger**

If a control in a certified bundle changes (EDR version updated, proxy config
changed, SOC workflow modified, agent tool scope changed), the bundle is
temporarily invalidated. Any risk acceptance record relying on that bundle
must be re-evaluated within 5 business days. During that window, the residual
risk level defaults to the level that would apply WITHOUT the bundle.

### 12. Adversarial Validation  (revised)

Current §12 is a cadence table. Expand to integrate with the control stack
assessment (§6.2):

Add as a distinct activity:

| Activity | Cadence | Scope |
|----------|---------|-------|
| **Control bypass testing** | Annual minimum per control family | EDR bypass, network segmentation bypass, DLP evasion, SOC alert evasion |
| **Agentic attack simulation** | Annual minimum | Agent tool privilege escalation, prompt injection to data access, agent-to-agent propagation, model supply chain attack |
| **Detection validation** | Quarterly | For every SIEM rule covering a compensated exposure: can we trigger it? Would the SOC notice? |

These activities feed directly into the control bundle certification in §6.4.
A control that has never been bypass-tested cannot be part of a certified
bundle — only *deployed* controls can.

### 14. Architectural Exposure Patterns  (NEW)

A catalog of architectural patterns that eliminate exposure classes rather than
reacting to them. Every pattern documents what exposures it eliminates, what new
exposures it introduces, maturity stages, and verification criteria.

| Pattern | Surface Eliminated | Example |
|---------|-------------------|---------|
| **Presentation-Layer-Only Access** | Client-side software vulnerabilities; reduces endpoint to browser | Replace RDP/VPN + thick client with web-based access via secure browser gateway |
| **Ephemeral Workloads** | Long-lived vulnerabilities; every deployment is clean | Immutable containers, serverless, CI/CD-driven replacement |
| **Zero-Trust Network Access** | Network-level exposure; every request is per-session, per-app | ZTNA broker replaces VPN |
| **Agent-Mediated Access** | Direct human access to sensitive surfaces; agent brokers all interactions | Users interact via AI agent with controlled, audited tool access and no direct credential delegation |
| **Browser Isolation** | Web-based client-side exposure | Remote browser isolates execution; user sees a rendered stream |
| **Data-in-Place Architecture** | Data exfiltration paths; data never leaves the trust boundary | Queries run against data; results are aggregated, not raw; no bulk export |

Each pattern includes:
- What exposure classes it eliminates
- What new exposures it introduces (every architecture has trade-offs)
- Implementation stages (Minimum → Good → Adaptive)
- Verification criteria
